02 · Why this projectMake academic records easier to manage

ProblemSeparate, manual records

Student details, marks, and attendance are easy to duplicate or calculate inconsistently when managed by hand.

MotivationOne practical desktop workflow

Connect common record tasks with reusable Java classes and clear separation between screens, logic, and storage.

Objective 01
Organize records

Add, find, update, and remove students and courses.

Objective 02
Calculate results

Compute totals, grades, percentages, and attendance eligibility.

Intended operator
Academic staff demo user

The app provides an admin-style demo login; it has no student portal or role system.

11 · OOP foundationA class is the plan; an object is one record

WHAT
Class and object

A class defines fields and behavior. An object is a created instance carrying values for those fields.

WHERE / WHY
model.Student and DemoData

Student models shared identity and academic fields. Each object is one student's state, passed to services and displayed in a table.

12 · OOP conceptEncapsulation keeps state behind a class API

WHAT

Keep an object's fields private and expose deliberate methods to read or change them.

WHERE

Person, Student, Course, Marks, and Attendance use private fields.

HOW

getName() reads the name; setName(String name) updates it.

WHY

Callers use a stable API instead of directly depending on the storage layout.

Person.java private String name; public String getName() { return name; } public void setName(String name) { this.name = name; }

The setters themselves are simple assignments; form and service validation happen elsewhere.

13 · OOP conceptStudent and Teacher reuse Person

WHAT

Inheritance lets a child class reuse and extend a parent class's behavior and data.

WHERE

Student extends Person and Teacher extends Person.

HOW

Each child constructor calls super(id, name, age, phone, email), then assigns its own fields.

WHY

Shared person details live once; student/employee details stay in their specific class.

<<abstract>> Personid · name · age · phone · email
extends ↓
StudentstudentId · department · semester · section · admissionYear
TeacheremployeeId · department · designation
Student(...) { super(id, name, age, phone, email); // assign Student-specific fields }

14 · OOP conceptPerson defines the shared contract

WHAT

Abstraction exposes the common idea while leaving type-specific details to concrete classes.

WHERE

public abstract class Person and displayDetails().

HOW

Person cannot be instantiated directly. Student and Teacher provide the method body.

WHY

Both person types share identity fields while retaining their own details display.

Person.java public abstract class Person { private int id; private String name; public abstract void displayDetails(); }

The method declarations exist in the source. The Swing screens do not currently call displayDetails().

15 · Polymorphism AOverloading: same name, different parameters

WHAT / WHY

Overloading gives related operations one readable name. The compiler chooses a signature from the argument types.

WHERE / HOW

StudentService.searchStudent(int) searches by numeric ID; searchStudent(String) searches by name.

The ID/name branches in StudentPanel.performSearch() call the matching overload.
StudentService.java public List<Student> searchStudent(int studentId) public List<Student> searchStudent(String name) // Actual call forms used by StudentPanel: studentService.searchStudent(3); studentService.searchStudent("Amit");
Also in Marks.java public char calculateGrade(int marks) public char calculateGrade(double percentage)

16 · Polymorphism BOverriding: child supplies its own behavior

WHAT

A subclass replaces an inherited method body while keeping the same signature.

WHERE

Student.displayDetails() and Teacher.displayDetails() override the abstract method in Person.

HOW

@Override asks the compiler to check the matching signature; runtime dispatch uses the object's class.

WHY

Shared parent-facing code can work with different person types without knowing each subtype's fields.

Actual method signatures public abstract void displayDetails(); // Person @Override public void displayDetails() { ... } // Student @Override public void displayDetails() { ... } // Teacher
Valid dispatch example using DemoData values Person p = new Student(1, "Amit Kumar", 20, "9876543210", "amit@example.com", "STU001", "Computer Science", 4, "A", 2022); p.displayDetails();

This valid dispatch example uses real project classes and demo values; the GUI does not invoke displayDetails().

17 · OOP conceptInterfaces separate a promise from an implementation

WHAT

An interface declares operations that an implementing class must provide.

WHERE

Four repository contracts plus interface_.ReportGenerator.

HOW

InMemoryStudentRepository implements StudentRepository; three nested report generators implement ReportGenerator.

WHY

Services can accept a repository contract; report types share a common generation API.

StudentRepository.java public interface StudentRepository { void save(Student student); Student findById(int id); List<Student> findAll(); void update(Student student); void delete(int id); }
ReportGenerator.java public interface ReportGenerator { String generateReport(List<?> data); String getReportTitle(); } // Implemented by three nested report classes // inside ReportPanel.

18 · Java detailsConstructors, access, static state, and value identity

Constructor overloading + injection

StudentService() chooses InMemoryStudentRepository; StudentService(StudentRepository) accepts a dependency. AppSession uses the default constructor.

Access modifiers

Model state is private; getters/setters and service operations are public; helpers such as validateMarks() are private.

Static members

Marks.MAX_INTERNAL and Attendance.ELIGIBLE_PERCENTAGE are constants. Repository lists and AppSession services are static.

Object relationships

Panels hold service references; services hold repository references. Marks and Attendance link records through student/course IDs.

Course.java @Override public String toString() { ... } @Override public boolean equals(Object o) { ... } @Override public int hashCode() { return courseId.hashCode(); }
Course equality uses courseId; its hash code uses the same key. Person, Student, and Teacher also override toString() with readable details.

21 · ValidationReject bad input before it reaches storage

Reusable checks

ValidationUtil checks email, 10-digit phone, age, IDs, credits, marks, and attendance ranges.

UI checks

StudentPanel.validateForm() requires a name, numeric age, 10-digit phone, email format, and non-empty student ID.

Service checks

StudentService.addStudent() rejects null, empty name, or age outside 15-60.

Error handling

Panels catch exceptions and show a Swing error dialog; model methods throw IllegalArgumentException.

ValidationUtil.java private static final Pattern PHONE_PATTERN = Pattern.compile("^[0-9]{10}$"); public static boolean isValidPhone(String phone) { if (!isNotEmpty(phone)) return false; return PHONE_PATTERN.matcher(phone).matches(); }

Verified gap: the student form checks that its ID is non-empty, but does not call isValidStudentId(); the service also does not enforce ID format or student-ID uniqueness.

24 · Current limitationsWhat the code does not yet provide

StorageSession-only data

Repositories hold static ArrayList values; restarting the app loses user changes.

AuthenticationDemo login only

Credentials are hard-coded in LoginFrame; no secure account store or roles.

ExportNot implemented

The Export button only shows a “coming soon” dialog.

Report valueOverall report has a placeholder value

It prints total courses as hard-coded 0; its “top performing” heading does not sort students.

Teacher managementModel only

Teacher exists, but no teacher panel, service, repository, or report exists.

ValidationSome checks are not wired into forms

Student ID format/uniqueness are not enforced by the add flow.
